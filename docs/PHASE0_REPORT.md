# Phase 0 기술 검증 보고서

- 작성일: 2026-10-23
- 환경: macOS 27.0.1 (Apple Silicon), Swift 6.4 (Command Line Tools, **Xcode 없음**), Rust 1.91.1
- 상태: **방안 A(IMK keyUp) 폐기, 방안 B(CGEventTap 물리 키 스트림) + C(타이머 폴백) 채택.** TextEdit·Safari·Chrome 자동 타건 테스트 통과. 미해결 1건(5절)

## 1. 만든 것

| 항목 | 위치 | 비고 |
| --- | --- | --- |
| 엔진 프로토타입 | `crates/semoe-core` | 한 번에 모아치기(키뗌 + 40 ms 타이머), 아랫글쇠, 모음·종성 시프트, 기본 결합 규칙 일부, 스페이스 모아치기, 낱자 단위 Backspace. 테스트 15개 |
| C ABI | `crates/semoe-ffi` (`include/semoe.h`, `module.modulemap`) | 계획서 4.2와 같은 함수 7개, `catch_unwind`, 테스트 3개 |
| macOS 입력기 | `macos/SemoeIME` | `IMKInputController`, keyCode → HID usage 변환, marked text, `DispatchSourceTimer`, 메뉴(키뗌 사용 on/off, 로그 on/off) |
| 물리 키 스트림 (방안 B) | `macos/SemoeIME/KeyTap.swift` | 별도 스레드의 세션 이벤트 탭(listenOnly)으로 keyDown·keyUp을 물리 순서와 하드웨어 시각 그대로 기록. IMK keyDown과 짝을 맞춰 엔진에 순서대로 넣는다. 권한 없으면 자동으로 타이머 전용 |
| 개발용 서명 | `scripts/setup-dev-signing.sh` | 자체 서명 인증서(별도 키체인 `~/.semoe-dev`). 재빌드해도 입력 모니터링 권한 유지 |
| 이벤트 로그 | `~/Library/Logs/SemoeIME/events.tsv` | 앱별 keyDown/keyUp, 이벤트 지연, 타이머 발화 지연 기록 |
| 스크립트 | `scripts/` | `build-rust-universal.sh`, `build-macos.sh`, `install-dev.sh`, `tis.swift`, `analyze-events.py`, `make-icon.swift` |

엔진은 키 식별자(`SemoeKey`)로 **USB HID usage**를 쓴다. macOS keyCode, Linux evdev, Windows 스캔 코드 모두 이 값으로 바꿀 수 있어 플랫폼 중립 키로 알맞다.

빌드 관련 발견

- Xcode가 없어 XcodeGen/`xcodebuild` 대신 `swiftc`를 아키텍처별로 두 번 돌려 `lipo`로 합치는 방식으로 빌드했다. 의존성이 없고 CI에서도 단순하므로 Phase 3에서도 이 방식을 유지할지 검토한다.
- x86_64 링크 시 `libswiftCompatibilityPacks.a`에 x86_64 슬라이스가 없다는 경고가 나오지만 링크와 실행에는 문제없다.
- C 헤더의 `#define` 상수는 Swift에서 `Int32`로 들어와 타입이 맞지 않는다. `static const uint32_t`로 선언해야 한다(cbindgen 설정 시 주의).
- 모드가 있는 입력기(`ComponentInputModeDict`)는 상위 소스(번들 ID)와 모드를 모두 켜야 한다.
- 새로 설치한 입력기는 처음 한 번 사용자가 시스템 설정에서 추가해야 프로그램으로 선택할 수 있었다(그 전에는 `-50`).
- 입력기 프로세스를 `pkill`하면 시스템이 바로 다시 띄우지 않는다. 그동안 열린 문서는 영문이 그대로 들어가므로 `install-dev.sh`가 설치 후 직접 실행한다.
- ad-hoc 서명은 빌드마다 cdhash가 바뀌어 TCC 권한(입력 모니터링)이 풀린다. 개발 중에는 로컬 자체 서명 인증서로 서명하면 유지된다(Phase 3에서 정리).

참고: 스모크 테스트 도중 세모이 대신 기존 입력기(타닥)가 선택된 채 합성 키 입력이 들어갔는데, 타닥은 같은 합성 chord를 `간강 흙` 등으로 모아 입력했다. macOS에서 다른 입력기가 모아치기를 구현하고 있다는 정황이지만, 키뗌을 어떤 경로로 받는지는 확인하지 않았다.

## 3. 앱별 IMK keyUp 수신 결과 (방안 A)

사용자가 각 앱에서 모아치기로 입력한 로그(`events-imk-only.tsv`)를 `scripts/analyze-events.py`로 요약했다. 단위 ms.

| 앱 | keyDown | keyUp | 이벤트 지연 p50 | p99 | 타이머 지연 p50 | p99 | 최대 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| TextEdit | 25 | **0** | 0.40 | 0.56 | 1.12 | 1.15 | 1.15 |
| Safari | 117 | **0** | 0.45 | 12.64 | 1.10 | 1.28 | 1.28 |
| Chrome | 64 | **0** | 0.22 | 0.86 | 0.68 | 1.09 | 1.09 |
| Dia | 51 | **0** | 0.37 | 0.62 | 0.92 | 1.12 | 1.12 |
| Terminal | 55 | **0** | 0.30 | 0.85 | 0.98 | 1.73 | 1.73 |
| VS Code | 63 | **0** | 0.26 | 3.49 | 1.08 | 1.13 | 1.13 |
| IntelliJ | 90 | **0** | 0.32 | 0.62 | 0.90 | 1.13 | 1.13 |
| Pages | 80 | **0** | 0.32 | 0.57 | 1.07 | 5.29 | 5.29 |
| Word | 61 | **0** | 0.35 | 0.74 | 1.07 | 1.19 | 1.19 |
| Raycast | 28 | **0** | 0.36 | 0.61 | 1.09 | 19.07 | 19.07 |

- `recognizedEvents`에 `.keyUp`을 넣어도 **IMK는 keyUp을 입력기에 전혀 넘기지 않는다.** 앱 종류(AppKit, Electron, JetBrains, 브라우저, Office)와 무관하다.
- 이벤트 지연(NSEvent.timestamp → 입력기 수신)은 거의 1 ms 미만이다. Safari·VS Code에서 p99가 3~13 ms로 튄다.
- `DispatchSourceTimer`(strict, leeway 1 ms)는 마감보다 약 1 ms 늦게 발화한다. 최악값은 Pages 5 ms, Raycast 19 ms였다. 40 ms 타이머를 쓰기에 충분하다.
- 같은 시간 동안 엔진은 keyUp이 없으므로 타이머로만 확정했다. 사실상 방안 C로 동작한 셈이다.

## 4. keyUp 방식 결정

**방안 A는 폐기한다. 방안 B(물리 키 스트림)를 기본으로 하고, 방안 C(타이머 전용)를 폴백으로 둔다.**

### 4.1 처음 시도(탭으로 keyUp만 받기)가 실패한 이유

탭으로 keyUp만 받고 keyDown은 IMK에서 받았더니 chord가 낱자로 쪼개졌다. 로그로 확인한 원인은 둘이다.

- **IMK keyDown 시각을 믿을 수 없다.** 앱은 keyDown을 하나 처리하는 동안 다음 keyDown을 붙잡아 두었다가, 넘기는 시점의 시각을 붙인다. 예: `ㄱ`을 누르고 3 ms 뒤에 누른 `ㅏ`가 `ㄱ`을 뗀 뒤 11 ms 시점에 눌린 것으로 기록됐다.
- **IMK keyDown 자체가 늦다.** 물리적으로 누른 시각부터 IMK가 넘길 때까지 p50 11~23 ms, p99 66~95 ms 걸렸다. 앱이 막 활성화된 직후의 첫 타건이 특히 느리다.

### 4.2 채택한 구조

1. **탭 스레드**가 keyDown·keyUp을 물리 순서와 하드웨어 시각 그대로 기록한다. 메인 스레드와 따로 돌기 때문에 IMK 호출로 메인 스레드가 바빠도 밀리지 않는다.
2. **IMK keyDown이 오면** 기록에서 같은 키의 keyDown을 찾는다. 그 앞에 있는 keyUp들을 먼저 엔진에 넣고, 이어서 keyDown을 물리 시각으로 넣는다.
   - 짝 앞에 있는데 짝이 없는 keyDown은 입력기로 오지 않은 키이므로 버린다. IMK는 keyDown을 물리 순서대로 넘기기 때문이다.
3. **keyUp은 기록되는 즉시 처리한다.** 단, 아직 IMK 짝을 기다리는 keyDown 뒤에 있는 keyUp은 그 keyDown이 처리될 때까지 기다린다.
4. **타이머가 울려도**, 마감 전에 눌렸지만 아직 IMK로 도착하지 않은 keyDown이 기록에 있으면 확정을 미룬다(2 ms 간격으로 다시 확인).
5. 엔진(`semoe-core`)은 늘 물리적으로 올바른 순서를 받으므로 순서 보정 로직이 필요 없다. 두 macOS 이벤트 경로를 맞추는 일은 macOS 껍데기가 맡는다.

### 4.3 자동 타건 테스트

합성 키 이벤트(`CGEventPost`, HID 수준)로 아래 패턴을 연달아 입력했다. 기대값은 `간간강 흙간간가ㄱㅏ가ㅇ` + Return.

| 패턴 | 기대 |
| --- | --- |
| `k f s` chord / `s k f`(순서 바꿈) | 간 / 간 |
| `k f a Space` chord | `강 ` |
| `h g e x` chord (겹받침) | 흙 |
| 간격 없이 셋을 누르고 바로 뗌 | 간 |
| 간을 누른 채 일부만 떼고 다음 가를 누름 | 간가 |
| ㄱ을 누르고 80 ms 뒤 ㅏ (타이머가 먼저 확정) | ㄱㅏ |
| 가를 떼고 5 ms 뒤 종ㅇ — 키뗌 확정이어야 `가ㅇ`, 타이머 전용이면 `강` | 가ㅇ |

| 앱 | 결과 |
| --- | --- |
| TextEdit (매번 새로 실행) | 3/3 일치. 첫 타건이 70 ms까지 늦었지만 4번 규칙으로 해결 |
| Safari (로컬 테스트 페이지) | 4/4 일치 |
| Chrome (로컬 테스트 페이지) | 2/2 일치 |

로그 요약(`analyze-events.py`, 단위 ms):

| 앱 | IMK keyDown | 짝 없음 | keyUp | 유실 | IMK 지연 p50 | p99 | 타이머 p50 | p99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| TextEdit | 112 | 0 | 111 | 1 | 23.2 | 73.3 | 1.1 | 35.0 |
| Safari | 84 | 0 | 84 | 0 | 11.6 | 66.3 | 1.1 | 27.3 |
| Chrome | 56 | 0 | 56 | 0 | 11.5 | 95.3 | 1.2 | 56.4 |
| Warp (사용자 직접 입력) | 26 | 0 | 26 | 0 | 5.8 | 28.1 | 1.1 | 1.2 |

- TextEdit의 유실 1건은 앱 종료 직전의 Return이다.
- 타이머 p99가 큰 것은 4번 규칙으로 확정을 미룬 시간이 포함되었기 때문이다.
- 실제 IDE·터미널·문서 앱에는 명령 실행이나 파일 변경 위험이 있어 합성 키를 보내지 않았다. 탭은 세션 전체의 키를 보므로 앱에 따라 달라지는 것은 IMK 지연뿐이고, 같은 구조로 동작할 것으로 본다.

## 5. 미해결

- **입력기 연결이 끊긴 사례 1건**: 테스트 중 입력기 프로세스가 바뀌었다. 직전 마지막 기록은 TextEdit의 파일 열기 창(`openAndSavePanelService`)에서 받은 keyDown 2개였다. 새로 뜬 프로세스는 어느 앱과도 연결되지 않아, 그동안 Safari에서는 글자가 사라졌다(Return만 전달됨). 입력기를 재시작하자 정상으로 돌아왔다.
  - 크래시·멈춤 보고서는 없었고, 같은 조건으로 다시 해 봐도 재현되지 않았다.
  - 의심: 타이머나 탭이 handle() 밖에서 원격 패널 클라이언트에 `insertText`를 호출하다 멈췄고, 시스템이 프로세스를 종료시켰을 수 있다.
  - 조치: 프로세스 시작 시 `launch` 로그를 남긴다. Phase 3에서 클라이언트 호출 시간 제한과 연결 상실 감지를 검토한다.

- **결합 규칙 누락 (해결)**: 처음에는 결합 규칙을 계획서 표를 보고 손으로 옮겼는데, 빠진 규칙이 있어 `됐`이 `됬ㅏ`나 `되ㅏㅆ`로 나왔다. 이제 XML `UnitMixTable`에서 현대 한글 규칙(초성 18, 중성 35, 종성 62)을 뽑아 쓴다. `됐`은 다섯 키의 120가지 순서 모두에서 테스트를 통과하고, Safari 실입력도 확인했다.
  - 원본 데이터 자체가 순서에 따라 결과가 다른 경우가 있다. 예: `ㅓ+ㅣ` 규칙이 없어서 `ㅜ+ㅓ+ㅣ`는 순서에 따라 ㅞ가 안 된다. 날개셋 실제 동작과 대조할 항목이다.

- **키보드 재밍 (대응)**: 맥북 내장 키보드에서 `뺨`(초ㅂ·초ㅇ·모음시프트·ㅡ·종ㅁ, 다섯 키)이 `뺘ㅁ`으로 나왔다.
  - 로그를 보면 네 키를 누른 동안 `z`(종ㅁ)의 keyDown이 오지 않다가, `g`·`j`를 뗀 지 0.2 ms 만에 들어왔다. 키보드가 동시 입력 한계 때문에 키를 늦게 보낸 것이고, 그사이 40 ms 타이머가 `뺘`를 확정했다.
  - 시도했다가 롤백한 것: 키가 하나라도 눌려 있으면 타이머로 확정하지 않는 옵션(`hold_while_pressed`, 안전 한도 1초). 합성 키 재현에서는 대체로 `뺨`이 나왔지만, 실사용에서는 여전히 잘 되지 않아 걷어냈다. 진단용 `commitComposition` 로그는 남겼다.
  - 결정: 키보드 한계는 엔진 동작으로 받지 않는다. 대신 `뺨`을 추가 약어 `ojz`(초ㅂ+초ㅇ+종ㅁ)로 등록한다(계획서 2.5, Phase 1·2).
